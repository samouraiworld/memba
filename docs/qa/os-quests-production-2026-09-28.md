# Memba OS Quests production QA

28 September 2026. This feature audit follows Validators PR #1356 in the ordered OS audit stack. Feed/Live, Tokens, NFT Marketplace, App Store and Profile have separate active sessions and are outside this PR.

## Scope and production baseline

The audit covers the OS and classic Quest Hub, catalog and quest detail, completion and proof submission, reviewer queue, leaderboard, ranks and XP, candidature unlock, attestation vouchers, and the Points route. Guest journeys were checked on `https://memba.club/os/quests` and its classic route at desktop and 390 px phone widths. No production wallet was connected; no quest was completed, claim reviewed, voucher submitted, or transaction broadcast during live QA. Local tests and stubbed browser fixtures cover private and failure states.

Production guest testing found that returning from a detail lost Hub filters, a populated leaderboard's Quest count clipped at 390 px, and the deployment proof field lacked a persistent label. The Points route disclosed its coming-soon state and guest Admin showed a reviewer gate. Local 360 px OS testing additionally reproduced a leaderboard whose XP column was entirely offscreen. The deeper code and backend audit found that 16 specialized deployment quests could award 685 verified XP from generic namespace/path evidence that did not prove their advertised package or realm semantics. Two hidden coming-soon deploy IDs were also server-claimable. This could satisfy the 350 verified XP candidature threshold without the advertised work.

## Ten review perspectives

| Perspective | Finding and response |
|---|---|
| Live guest journey | Filtered Hub state disappeared on detail return. Hub filters now live in the URL and detail/back links preserve them. The deploy proof input has a label and network/coming-soon states remain explicit. |
| Security and abuse | Generic deploy verification accepted specialized IDs and nonlive off-chain triggers; cross-wallet asynchronous responses could write another member's local progress. The backend admits only curated claim types and deployment proof kinds; frontend completion and sync capture the initiating wallet, and claim submissions reject mismatched tokens. Claim review and verified completion are transactional. Pending claims for retired quests can be rejected but cannot be approved into new XP or vouchers. |
| Accessibility | Reviewer loading, error and empty states were conflated, claim actions lacked unique names, and status changes were quiet. Admin now distinguishes these states, labels each action by quest and applicant, offers retry, and moves focus after review. Deployment results are announced. |
| Architecture and performance | Hub and leaderboard fetched while parked OS windows were inactive; leaderboard usernames fanned out without a bound, and stale responses could replace new wallet state. Window activity, request cancellation, wallet keys and bounded username workers now limit work and stale updates. |
| Routes and state | Filter, search and page state did not survive detail and leaderboard navigation; old detail verification could appear on a new quest or wallet. URL-backed filters/pagination and keyed verification sessions make navigation stable. |
| Operational reliability | Attestation reads treated RPC failure as an empty recorded set, risking duplicate transactions. Read failures now surface with retry and cached vouchers are hidden until on-chain status can be confirmed. Pending self-report claims refresh when the page regains focus and while visible; stale responses cannot undo a newer review or submission. The leaderboard repairs stale existing-user rank cache entries and quest sync deduplicates costly verifier calls. |
| Visual and responsive design | A 360 px OS leaderboard hid XP despite correct phone styles; the quest XP badge wrapped. Container-aware table rules, a fixed-line XP badge and compact narrow-window Hub spacing keep core information visible. |
| Product and content | Specialized deploy titles promised code semantics that a path check could not prove, and a faucet claim inferred provenance from any funded account. Only a package and a realm ownership claim remain live, with truthful descriptions; specialized deployments, dependent full-dApp claim and faucet remain visible as coming soon. Candidature prompts in Quests and Home read backend verified XP and network availability; local XP no longer creates a sidebar eligibility badge. Candidature distinguishes verification in progress from unavailable XP and offers retry; the Hub labels saved local XP when a server refresh fails. |
| Cross-browser and device | Chromium and Firefox guest journeys passed at 360 px OS windows and 320/390 px phone widths for Hub filters, detail return, leaderboard, Admin gate and Points. No horizontal page overflow was found. |
| Catalog and historical data | A frontend/backend parity review found that old specialized deployment rows could still inflate verified XP even after new claims were gated. Retired claims remain in total XP/history but are excluded from verified XP and new attestation vouchers. A nonlive 1000-XP derived milestone is no longer newly granted. Curated catalog/claimable-set parity is guarded by a backend test. |

## Verification and limits

- Production testing was guest and read only. Authenticated verification, reviewer approval, candidature broadcast and attestation submission were exercised with unit/service tests or local fixtures, not a production wallet.
- Full frontend ESLint, the production build, focused Quests/Home eligibility/attestation tests, and the full backend service test package passed after the rebase and review fixes. The earlier broad Vitest run passed 7,280 tests across 707 files; one unrelated `gnoToolchain.test.ts` case fails because its local toolchain cannot resolve `chain/runtime/unsafe`. The same case fails unchanged on the Validators base branch, so this PR does not introduce it. The Quests OS Playwright regressions previously passed 4/4 in Chromium and Firefox for URL return and the populated 360 px leaderboard. A separate read-only browser pass covered six viewport/engine combinations. Current-head hosted CI still needs to complete after the branch is pushed.
- Historical total XP and completion rows are preserved for transparency. An attestation already broadcast on-chain cannot be revoked by this change; the server can withhold old uncertain vouchers and exclude those rows from future verified XP calculations.
- Production Fly currently accepts only the `gnoland-1` wallet chain and the quest RPC fallback targets mainnet. Hidden retired test13/topaz deep links can still render old realm availability, but cannot complete authenticated quests. If another network is re-enabled, the backend must bind verification to that chain before its quests are advertised. Deploy the backend reward gates before exposing the revised frontend catalog; a frontend-only deployment would leave the old direct RPC claim path open. A post-deployment guest smoke is required after the ordered PR stack lands.
